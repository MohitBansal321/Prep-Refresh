# Recognition Diagram — Fast & Slow Pointers

Use this diagram when you are staring at a new problem and trying to decide whether it fits the Fast & Slow Pointers pattern, or whether it actually needs a different tool.

```mermaid
flowchart TD
    Start([Read the problem statement]) --> Q1{Is the input a linked list,<br/>OR a sequence generated by<br/>repeatedly applying some<br/>function to a value?}

    Q1 -- No --> OtherStructure[Probably a different family —<br/>array/string, tree/graph, etc.]

    Q1 -- Yes --> Q2{Do you need to detect a<br/>cycle / repeat / "meeting point",<br/>or find the middle without<br/>counting length first?}

    Q2 -- No, I need to reverse<br/>the whole list or a range --> InPlaceReversal[Use In-place Reversal<br/>see ../in-place-reversal/]

    Q2 -- No, I just need to<br/>check membership --> HashSet[Consider a hash set /<br/>hash map instead —<br/>but note the O(n) space cost]

    Q2 -- Yes --> Q3{Is O(1) extra space<br/>a hard requirement,<br/>or at least strongly preferred?}

    Q3 -- No, extra memory is fine --> HashSetOk["A hash set of visited nodes<br/>also works (O(n) space) —<br/>Fast & Slow is still better,<br/>but not strictly required"]

    Q3 -- Yes --> UseFSP["USE FAST & SLOW POINTERS<br/>(Floyd's Tortoise and Hare)"]

    UseFSP --> Q4{Need the cycle's<br/>START node, not just<br/>whether one exists?}
    Q4 -- Yes --> Phase2[Run Floyd's Phase 2:<br/>reset one pointer to head,<br/>advance both by 1 step]
    Q4 -- No --> Done1[Phase 1 alone is enough]

    style UseFSP fill:#2f6f4f,color:#fff
    style Phase2 fill:#2f6f4f,color:#fff
```

## How to read it

Start at the top and answer each diamond honestly before moving on — the diagram is a decision tree, not a checklist to skim. The first gate (`Q1`) filters out anything that is not fundamentally a "list of things linked one-to-the-next" or "value derived from the previous value" — Fast & Slow Pointers has no purchase on a problem shaped like a static array with random access, because the whole point of the pattern is walking pointers/values forward, not indexing into them.

The second gate (`Q2`) is the actual recognition signal: the phrase to listen for in a problem statement is "detect a cycle," "does it repeat," "find the middle," or "two things that eventually meet." If the ask is instead "reverse" or "rewire," you want the sibling pattern, **In-place Reversal**, not this one.

The third gate (`Q3`) is where Fast & Slow earns its keep over the naive alternative: a hash set of visited nodes solves cycle detection too, but at O(n) space. If the problem explicitly says "O(1) space" (a very common LeetCode/interview constraint on linked-list problems), that phrasing is itself the strongest signal to reach for this pattern.

The final branch (`Q4`) captures a detail people forget: detecting *that* a cycle exists (Phase 1) and finding *where* it starts (Phase 2) are two different questions requiring an extra step. If a problem asks for the entry node (like LeetCode 142), you need both phases, not just the first collision.
